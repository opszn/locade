# Locade 竞品初查

初查：2026-10-20；公开文档复核：2026-10-21（Asia/Shanghai）。方法：GitHub 公开仓库搜索、仓库 README 与产品官网查阅。**没有安装或实测竞品，也不是穷尽市场或商标排查。** 页面和功能可能继续变化。

以下是文档公开声明的能力，不是对实现质量的独立验证。「未见强调」不等于「一定没有」。不以 stars 或最后推送日期判断实际体验和成熟度。

## 1. Portbook：最直接的发现类竞品

来源：https://github.com/a-grasso/portbook

README 明确描述：

- 自动发现 localhost HTTP 开发服务，从进程 cwd 与网页 title 识别项目。
- 可点击的 Web 项目卡片，SSE 更新，live / error / dead 分类。
- CLI、TUI、JSON 输出与诊断命令；支持 macOS / Linux。
- 声称约 5 MB 的 Rust 静态二进制（另依赖系统 lsof / ss）。

影响：Locade 的「自动发现 + 项目名 + 目录关联 + 打开」不是独创，也不能凭 React / Node 原型声称更轻、更快。对端口识别和诊断优先的用户，Portbook 可能更合适。

我们可以验证的差异：以可长期收藏和找回的视觉作品库为中心，处理项目身份、离线封面与回到开发现场；该 README 的重点仍是运行中服务的可发现性与诊断，不足以据此断言它没有任何持久化或截图能力。

## 2. Hotel：本地服务目录与启动

来源：https://github.com/typicode/hotel

README 明确描述：

- 从浏览器启动应用，使用本地域名和 HTTPS。
- 用户通过 `hotel add` 注册命令或地址，按访问启动服务。
- 可作为本地服务器目录；列有多种社区菜单栏 / 托盘工具。

影响：「本地服务目录 + 网页 + 托盘入口」有长期先例。Locade 不应仅通过一个菜单栏按钮就宣称差异化。

可选择的切入：优先收录用户在终端 / IDE 中已经运行的网页，不强制把所有项目迁入一个新的启动体系；先做好识别和找回，而非代理 / 域名 / 进程托管。

## 3. Port Radar：macOS 菜单栏端口管理

来源：https://github.com/juansebsol/port-radar-mac

README 明确描述：

- 原生 macOS 菜单栏，持续扫描监听端口、按项目分组。
- 通过本机 Apple Intelligence 解释进程，提供停止进程与 Cloudflare 隧道分享。
- 读取进程路径、参数与工作目录，不以 root 运行。

影响：菜单栏、自动端口发现、项目分组与本机隐私均已有产品覆盖。「AI 不上传」也不是 Locade 的独有优势。

切入差异：Locade 以作品预览、收藏与找回为中心；不以 AI 解释、任意端口停止或对外分享为主线。当前安全约定更窄：不停止外部启动的项目。

## 4. Harbor / Rack：菜单栏开发服务编排

来源：

- https://github.com/z1joey/harbor
- https://github.com/jafupy/Rack

README 明确描述：

- Harbor 提供 macOS 菜单栏和 TUI、项目配置、启动 / 停止 / 重启、日志与端口规划。
- Rack 提供 macOS 菜单栏、多命令并行、持久命名配置、工作目录与环境变量、日志和启停。

影响：如果 Locade 开始把主要精力放在日志、端口分配和多服务启停，就会进入现有编排工具赛道。

范围提示：本次未在 Harbor 仓库元数据中看到许可证；公开代码不自动等于可以按开源许可复用。竞品调研不构成代码复用授权。

## 5. LocalCan：相邻的本地开发网络工具

来源：

- https://localcan.com
- https://github.com/LocalCan/LocalCanApp

官网强调 Public URLs、隧道、本地域名、HTTPS、流量检查、Snapshot 分享与评论、CLI / MCP。公开仓库 README 明确说明它是闭源商业产品，该仓库用于问题与社区讨论；**不能因为它有 GitHub 仓库就称其开源**。

影响：它解决的主要是访问、分享和开发网络问题，能力比 Locade 原型丰富，但不是相同主任务。Locade 不做公网分享的定位是取舍，不是证明更先进；未来也可与它并用。

注意其 Snapshot 指向发布 / 分享静态版本，不应与 Locade 的本机截图封面混为一谈。

## 6. Vercel Labs dev3000 / d3k：截图也已进入调试工作流

来源：https://github.com/vercel-labs/dev3000

README 当前定位为 agent-first 本地 Web 调试运行时：管理开发服务器与浏览器，统一服务器日志、浏览器错误、网络、交互和截图；包含项目稳定浏览器 profile 与 Portless 地址。

影响：不能说「开发工具没有截图」或「AI 开发产生的项目没人管理」。d3k 更偏向代理驱动调试、证据采集与托管运行时，不以个人长期作品陈列为主要任务。

Locade 的独立浏览器 / 不继承登录态是隐私和复杂度上的取舍，不一定是体验优势：d3k 的稳定登录态恰好能服务登录流程调试。不要把竞品有意解决的问题描述成缺点。

## 结论与后续研究

- 存在直接、相邻和替代竞品；本次没有足够依据声称 Locade 首创或没有一比一同类。
- 「自动发现」「菜单栏」「本地保存」「截图」单项均不构成壁垒。
- 目前有一个视觉方向明确、核心链路跑通的原型；尚无性能、规模、分发或持续使用方面的已证实优势。
- 候选竞争力是项目级视觉记忆与找回：准确身份、离线保留、跨端口续接、明确授权和低配置负担。v0.3 已实现相关核心链路并有本机自动测试，但相对竞品的找回效率和长期价值仍需用户对比验证。
- 最真实的替代品还包括浏览器书签、IDE 最近项目、文件夹与终端历史；如果这些对目标用户已足够好，就不应为了差异化不断加功能。
- 公开发布前，另做同名产品 / 包名 / 域名 / 商标排查，并实际体验最直接的竞品。当前没有做名称清查，也没有执行上面仓库提供的安装脚本。

### Locade 现在能诚实主张什么

**事实：已实现的组合。** 当前版本将真实截图、离线保留的项目卡片、收藏 / 最近、目录 / 只读 Git 分支、显式编辑器入口和跨端口身份续接放在一个流程里。它面向「过几天我想找回那个做过的东西」，不只面向「此刻哪个端口在运行」。身份证据不足时保守分开，端口被另一目录的项目复用时不继承旧封面；这不是对任何项目都能自动去重的保证。

**建议定位，尚非验证结论：**「不是端口管理器，而是本地开发作品的视觉记忆库。」优先服务拥有多个小项目、实验和原型、容易忘记名称与端口的个人开发者；AI 辅助开发者只是可能更密集遇到这一问题的人群，不应把 AI 本身当作壁垒。

**假设：可能产生的用户价值。** 看封面比回忆项目名 / 端口更容易，服务离线时仍知道做过什么，恢复服务后仍回到同一张卡片，再从卡片回到源码目录 / 编辑器。这一整段闭环值得投入，但只有胜过浏览器书签、IDE 最近项目和最直接的 Portbook 才算优势。现有正向反馈只证明用户喜欢截图效果，不证明使用频率、留存或找回效率。

**不是当前可主张的优势：** 首创、没有竞品、唯一支持截图 / 本地存储 / 菜单栏 / 稳定身份、更轻、更快、全平台、功能更多或安全性已全面优于竞品。尚未逐个实测这些产品，也没有穷尽市场，不应把一张「有 / 无」表包装成护城河。

### 必须一起说明的短板

- 自包含 macOS 开发包约 340 MiB（本机磁盘占用），包含 Node 与 Chromium；Portbook README 声称约 5 MB 二进制。两者所带组件不同，不能直接比较内存 / 速度，但 Locade 显然还不能称为轻量分发。
- 只在当前 Apple Silicon Mac 做过验证；公开签名 / 公证、干净机器、Intel、真实登录启动和长期试用尚未完成。Portbook 文档已有 macOS / Linux，Hotel 声称跨平台，LocalCan 也有多平台入口。
- 不支持启停 / 日志 / 域名代理 / 公网分享；它们是本轮刻意的范围取舍，但对需要这些工作的用户确实意味着功能缺口。
- 截图不复用登录态，拦截远程资源与 WebSocket；认证页、CDN 或远程 API 页面可能不完整。实际项目不能因为界面精美就假定都能生成好封面。
- 自动身份识别仍可能遗漏或保守产生重复，旧资料迁移可能需手动绑定；准确识别与零配置不是已经完全兑现的无条件承诺。

### 下一步怎样验证「优势」

建议做同一批真实项目的任务对比：先保存 5–10 个项目，一周后在不知道端口的情况下找到指定项目、判断最近状态并回到源码。比较 Locade、Portbook、书签 / IDE 最近项目的完成时间、找错率、误关联 / 重复卡片数、人工配置量与一周后是否仍主动使用。只记录当前可用行为；离线卡片不等于能自动重新启动服务。没有这些结果前，对外讲清楚切入点，不讲未经验证的领先。
