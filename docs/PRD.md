# Locade 简版 PRD · v0.2–v1.0

日期：2026-10-20；执行授权更新：2026-10-21。状态：**用户已授权按本 PRD 自主开发与测试。具体完成情况以 [验收记录](ACCEPTANCE.md) 为准，不以本路线图本身代表已实现。**

## 1. 已有事实与待验证假设

- 已实现 v0.1：发现本机 HTTP(S) 网页、真实截图卡片、打开、手动地址、收藏、搜索、重命名与本地持久化。具体限制以 README 为准。
- 用户已试用并反馈「截图后的效果很不错」。这验证了初次视觉反馈，不等于已验证持续使用价值、发现准确率或分发方式。
- 用户同意讨论项目目录关联的下一步，同时要求明确 PRD、最终形态与竞品差异。本稿最初回应这些问题；2026-10-21 用户授权执行后已继续实现，具体进度见验收记录。项目启动 / 停止管理仍不在必选范围。
- 核心假设：有多个本地网页项目的人，会比记端口或文件夹名更容易通过截图找回作品，并愿意反复使用这个入口。

## 2. 定位与目标用户

**把正在做和曾经做过的本地网页，变成一个能认出、能找回、能继续开发的作品库。**

第一批目标用户：经常在多个前端、全栈、原型和个人实验项目之间切换的开发者，通常有多个项目与 worktree；使用何种 IDE 或 AI 编程工具不影响核心体验。

不是所有开发者都需要它。长期只做一个项目、主要开发无网页程序或已充分依赖现有启动器的人，不是第一优先人群。

核心任务：

1. 「这几个端口分别是什么？」——发现运行中的网页并认出它们。
2. 「上周那个橙色页面在哪？」——按截图找回离线作品与目录。
3. 「我要回去继续做它。」——打开网页、项目目录或编辑器；启动留作后续可选能力。

## 3. 建议的最终形态

**macOS 优先：菜单栏常驻入口 + 本地后台核心 + 默认浏览器中的完整项目库。**

```text
Locade.app（菜单栏入口、启动/退出后台核心、状态与最近项目）
    └── 本地核心（发现、身份关联、资料库、按需截图）
          ├── 浏览器项目库（完整卡片与管理界面）
          └── CLI（可选入口；不要求普通用户配置 Node）
```

- 菜单栏：搜索 / 最近访问 / 收藏 / 正在运行数量 / 打开项目库 / 刷新 / 退出。不在窄弹层塞完整卡片墙。
- 项目库：继续复用 React 界面，以截图和项目归档为核心；无需把网页重新实现成原生列表。
- 日常使用不要求用户保持终端窗口或手动安装 Node。开机启动必须由用户选择；退出 Locade 不终止外部启动的项目。
- 普通网页或 PWA 无法完成本机进程、目录关联；本地核心不可省略。所谓「网页版」仍然需要本机服务，不是托管到网站就能扫描用户机器。
- CLI 作为开源用户、开发者的辅助入口保留；不承诺尚未核查的 npm 包名，也不以 CLI 作为唯一面向用户的形态。
- 首发不承诺 Windows / Linux 菜单栏壳，但核心保留平台适配边界；「macOS 优先」与「永久仅 macOS」不同。

原稿曾暂不决定 SwiftUI / Tauri / Electron；2026-10-21 的本机分发实验采用 SwiftUI / AppKit，见第 9 节。源码编译、静态封装和本机原生运行测试通过；此前进程策略阻拦经用户手动放行后已复测，并修复退出等待死锁。公开分发门槛仍未通过。不能因为原生壳小就忽视 Node / Chromium 的实际体积与内存。

不优先做完整桌面主窗口：在验证稳定日用需求前，它增加内嵌浏览器和打包成本，却不直接改善项目识别或找回。后续如用户明显排斥浏览器标签页，可复用 Web UI 增加桌面窗口。

## 4. 产品模型：项目不是端口

当前 v0.1 主要按 URL 保留卡片。原稿识别的两个关键问题是：项目换端口会重复；另一个项目复用旧端口可能继承错误名称、收藏和截图。

v0.2 按以下模型实施（结果见验收记录）：

- Project：持久身份、名称、应用目录、工作树位置、收藏和封面。
- Endpoint：当前 / 历史地址、关联证据、最近探测时间、在线状态。
- Binding：自动识别或用户指定；用户指定优先，可纠正、解除和重新关联。

识别路径：端口 → 所属进程 → 工作目录 → 最近的应用目录 / Git 工作树候选。只在当前用户权限内查询，失败时明确显示「未关联」，不提权、不全盘扫描、不执行项目脚本。

不能仅用 Git 仓库根目录合并：monorepo 里可能有多个应用，worktree 也不能误并。优先依据规范化应用目录与工作树区分；同一目录下多个服务的角色不明确时允许用户确认，不强行归组。

稳定身份与关联证据缺失时宁可保持未关联，也不把旧截图展示给一个不确定的新进程。URL-only 旧数据迁移需保留原记录，避免猜测性合并。

## 5. 路线图与验收门槛

### v0.2：认得出、记得住

范围：

- macOS 进程工作目录候选与手动目录绑定。
- 展示项目名称、简略目录、Git 当前分支 / detached 状态；不改变分支或项目文件。
- Project / Endpoint 分离，处理换端口、端口复用、monorepo、worktree 与旧资料库迁移。
- 明确「最近探测」与「实时」的区别；分类展示未关联、离线、探测失败，增加隐藏 / 忽略入口。
- 在授权边界明确后，提供打开目录 / 编辑器的显式按钮；不提供任意 shell 命令接口。

验收：

1. 同一已关联项目从 3000 换到 3001，保留收藏与封面，不生成重复作品。
2. 不同项目先后占用 3000，不互相继承截图、名称或目录。
3. 同仓库不同应用、不同 worktree 不被无条件合并。
4. 自动识别失败仍可正常打开网页；手动绑定可纠正并跨重启保存，路径缺失有明确提示。
5. 分支读取只读；目录名、路径和进程参数不因日志 / API 意外泄露到外部。无需读取命令行全量参数来完成关联。
6. v0.1 数据可迁移且迁移失败可恢复；截图许可与删除行为不退化。

### v0.3：成为日用入口

范围：菜单栏壳、单实例 / 后台生命周期、可选开机启动、前台自动更新状态、最近项目与快捷入口、安装和卸载流程。

进入条件：v0.2 能可靠关联真实项目，用户有反复打开而非只看一次的需求。

验收：安装后无需单独配置 Node；关闭网页不丢收藏；开机启动可关闭；退出只终止 Locade 自身后台及它临时创建的截图浏览器；无截图任务时不常驻截图浏览器。

### v1.0：可靠的个人本地作品库

范围：稳定发现与去重、可靠的长期收藏、项目级截图排除、存储容量 / 清理入口、本地备份与恢复、错误诊断、可理解的权限说明、完善的分发更新流程。

启动功能作为可选扩展，不是 v1.0 必须堆入的条件。若确有需要，单独设计：用户明确选择目录并确认完整命令后才执行；只停止 Locade 自己启动且持续追踪的进程，绝不按端口随意杀进程。

## 6. 不做什么

交互验收补充（2026-10-22 用户明确要求）：站内确认、校验、执行状态与错误必须由 Locade 自有界面承载，不使用浏览器 alert / confirm / prompt 或原生表单校验气泡。所有破坏性后果明确展示，默认取消、可键盘操作；备份图片恢复单独选择，不以“取消”表达另一种恢复。文件选择 / 下载 / 显式打开网页或编辑器及系统授权仍尊重浏览器 / OS 集成边界，不伪造权限。动作矩阵与实际结果见 [交互验收](INTERACTION_AUDIT.md)。

- 不做部署平台、公开隧道、团队协作和云同步。
- 不做通用 Docker 管理、全功能进程管理器或 CPU / 内存监控面板。
- 不把 AI / MCP 接入变成基本使用前提；暂不因竞品都有就补同样的功能。
- 不自动执行从 package.json 或网页内容中发现的命令。
- 不默认扫描全部磁盘、读取源码正文、复用日常浏览器登录态或上传截图。
- 不承诺恶意网页沙箱；本地页面与查询参数也可能包含秘密，需要最小化存储与错误日志。

## 7. 成功标准（目标，不是当前测试结果）

优先验证三个问题，而不是先看 GitHub stars：

1. 有至少 5 个本地项目时，用户是否比书签 / 终端 / 文件夹更快找到指定作品？在控制环境中比较找回耗时、误选次数、首次配置负担。
2. 一周内，用户是否会在没有提醒时反复打开 Locade，且能说清它替代了哪个原来的步骤？用自愿访谈或本机记录验证，不默认上传遥测。
3. 地址变化 / 关闭重启后，是否仍准确地回到同一项目？身份测试和真实项目试用都必须覆盖。

性能和体积单独测量：发现耗时、截图耗时、空闲 CPU / 内存、安装体积、首次安装浏览器成本。2026-10-21 已增加[受控性能基线](PERFORMANCE.md)：仅已知本地地址探测、静态页截图、源码核心启动和核心空闲资源，不涵盖完整系统发现或整个应用资源。仍不把「轻量」写成已证实优势；不能靠持续高频扫描或常驻多个 Chromium 来维持体验。

## 8. 竞争策略

研究依据：[竞品调研](COMPETITIVE_RESEARCH.md)。

不是宣称「没有竞品」，也不是「截图功能独有」。争取的组合体验是：

**低配置发现 → 视觉识别 → 项目级持久身份 → 离线仍找得到 → 回到开发现场。**

2026-10-21 公开文档复核后的建议表述是：**本地开发作品的视觉记忆库**。重点回答「上周那个页面是什么，去哪里继续」，而不只回答「现在什么在运行」。Portbook 与发现 / 目录 / 卡片直接重叠，Hotel / Harbor / Rack 偏启停编排，LocalCan 偏访问分享，d3k 偏代理调试；它们也可能覆盖更多能力，不以文档未说明推断产品没有。

原型最初只有组合体验的前半段；本轮已补身份、离线目录找回与编辑器入口，但仍缺乏技术壁垒，尚无效率对比或长期留存证据。发现与目录识别已有直接竞品，菜单栏只是入口，隐私与不依赖 AI 也不是独家优势。需要靠稳定性、项目身份正确性、找回效率和克制的产品体验赢得选择。

差异化验收继续沿用第 7 节：同一批 5–10 个真实项目，一周后对比 Locade、Portbook、书签 / IDE 最近项目的找回时间、找错率、重复误关联和人工配置量。服务离线仍有卡片，不等于 Locade 能自动启动它；不为了比较表补齐日志、隧道或进程管理。

## 9. 执行授权与保留事项

用户已授权按「项目身份 / 目录关联 → 菜单栏与日用入口 → 资料管理与可靠性」推进完整 PRD 的本机实现与测试，无需逐项确认普通技术细节。默认采用本稿的目标用户与菜单栏 + 网页形态，不包含为竞争而增加服务编排。

本机实现选择原生 SwiftUI / AppKit 菜单栏壳，复用现有 Node / React 核心，自包含 Node / Chromium 打包验证。该选择不代表原型的视觉品牌已最终定稿，也不宣称已具备公开分发资格。

2026-10-23 用户已明确同意 MIT、个人 GitHub 仓库 opszn/locade，以及先私有 CI 后公开源码 Alpha。不包含 npm 或现有原生包分发；名称 / 包名 / 商标与正式 App 渠道仍需独立核查，实际发布状态见 RELEASE_STATUS.md。
